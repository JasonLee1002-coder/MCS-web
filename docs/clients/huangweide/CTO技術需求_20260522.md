## 模組 1：審核後台（最高優先）

### 需求描述

讓藥師用手機在 5 分鐘內完成一篇文章審核。

### 使用流程

```
行銷策略師
  → 設定主題（症狀 + TA + 商品方向）
  → AI 產出初稿

CMO AI
  → 自動禁字標記（不替換，只標紅讓人看）
  → 送進審核佇列

行銷審稿員（詩娟）
  → 手機後台看到文章
  → 修改文案 / 確認 SEO / 按「送藥師審核」

藥師（黃維德 / 在地藥師）
  → 手機收到通知
  → 讀文章 → 點「合規確認」或「需修改＋留言」
  → 5 分鐘內完成

系統
  → 自動排程發布到部落格 + GBP
```

### 技術規格要求

| 項目 | 需求 | 優先 |
|------|------|------|
| 手機友善後台 | PWA 或 mobile-first web | P0 |
| 審核狀態機 | 草稿→行銷審→藥師審→排程→發布 | P0 |
| 禁字標記 | 對照法規資料庫，自動高亮禁用詞 | P0 |
| 推播通知 | 藥師收到「有新文章待審核」| P0 |
| 發布到部落格 | 推進 huangweide-seo（Next.js MDX 或 CMS）| P0 |
| 發布到 GBP | Google Business Profile API | P0（CPO 已升 P0）|
| 版本記錄 | 每次修改都保留，可以 rollback | P1 |
| 多藥局架構 | 第 1 間用單一租戶，但程式碼要能擴展 | P1 |

### 問題想請 CTO 回答

1. 審核後台放哪裡最合適？（獨立 Next.js admin？還是整進 huangweide-seo？）
2. GBP API 整合的複雜度如何？需要 OAuth2 + Google My Business API，預估多少工時？
3. 禁字標記用 regex + 資料庫比對就夠了嗎？還是要 LLM 語意判斷（更準但更貴）？
4. 這個架構從第 1 間擴到第 5 間的邊際工時大概是多少？

## 模組 2：法規資料庫（知識庫）

### 需求描述

建立台灣衛生局裁罰案例資料庫，作為 AI 禁字規則的訓練依據。

### 資料來源

- 台北市政府衛生局官網「裁罰案例公告」
- 食藥署廣告違規案例
- 未來可擴展至新北市、台中、高雄

### 資料結構需求

```
{
  id: string,
  county: '台北市' | '新北市' | ...,
  date: date,
  company: string,
  product_type: '保健食品' | '化妝品' | '擦劑' | ...,
  violation_type: string,
  violation_words: string[],   // 被罰的違規詞
  fine_amount: number,
  source_url: string,
  ai_rule_derived: boolean     // 是否已轉成 AI 禁字規則
}
```

### 問題想請 CTO 回答

1. 爬蟲可行性：衛生局網站能爬嗎？有反爬機制嗎？
2. 建議用哪種儲存方式？（PostgreSQL / Supabase / 簡單 JSON？）
3. 從資料庫轉成「AI prompt 規則」的建議架構？
